## Code Map
- `gui/` — окно, маршрутизация режимов и worker orchestration.
- `core/` — pipeline, FFmpeg, STT, diarization и settings.
- - `stt_pool/` — STT-супервизор с пулом воркеров для `external-transcribe` (см. `doc/EXTERNAL_CLI_TRANSCRIBER.md`): `client.py` (тонкий клиент, ML-free: пачка входов, один дедлайн, `--priority`, `--max-parallel`), `queue.py`/`fsio.py` (файловая очередь v2 в `<root>/v2`, OS-lock супервизора, heartbeat), `config.py`/`keys.py` (лимиты из `stt_pool.json` → `ASKVLM_STT_POOL_CONFIG` → defaults; ключ воркера provider/model/compute/backend), `scheduler.py`/`estimates.py` (чистый планировщик: резервы слотов/потоков/commit/VRAM, spill `auto` на CPU по ETA, эвикция idle-воркеров других конфигураций, приоритеты с чередованием вызовов и старением; seed-оценки из бенчмарка + выученные), `supervisor.py` (цикл супервизора), `worker_setup.py` (опции `spec` и окружение запуска воркера; общие для супервизора и `tools/stt_concurrency` `memory-growth`), `procs.py`/`winjob.py`/`ipc.py`/`sysprobe.py` (процесс-воркер в своём Job Object с лимитом памяти, JSON-lines протокол, commit/nvidia-smi пробы), `worker.py`/`engine_api.py`/`engines.py` (процесс воркера; CPU-слоты = потоки над одной моделью, GPU = батчинг между заданиями). `--no-daemon` — legacy one-shot. `--stt-provider whisper|gigaam-ctc|gigaam-e2e-ctc` (Whisper по умолчанию; GigaAM в `.[ml]`; `gigaam-ctc` только CPU; `run.ps1`/`build.ps1` по умолчанию держат torch 2.10+CUDA). Виды заданий `stt` и `diarize` (псевдо-провайдер `sherpa-diarize`, только CPU, один слот на процесс); задания с новыми полями (`segments`, Whisper-опции, окно, диаризация) пишутся версией 2 файла задания, обычные — версией 1; структурный результат идёт в `data` (`segments` / `turns`); `external-transcribe --diarization` = два задания на вход со слиянием в клиенте; `external-diarize` — отдельная команда.
- - `stt_options.py` / `stt_output.py` — ML-free контракт структурного вывода: окно медиа, Whisper-опции декодирования, опции диаризации (wire-формы с валидацией); JSON-документы в формате `transcribe.py`/`diarize.py` навыка hardsub (единственное место сдвига и округления времён — `media_time`), назначение спикеров по максимальному пересечению, правило префиксов.
- - `diarization_models.py` / `sherpa_diarization.py` — CPU-диаризация sherpa-onnx 1.13.8 (pyannote segmentation 3.0 + WeSpeaker ResNet34-LM): закреплённые URL и SHA-256, загрузка в `.cache/models/sherpa-diarization/` через `.part` + атомарное переименование под межпроцессной блокировкой, извлечение одного члена архива; ленивые `numpy`/`sherpa_onnx`, новый экземпляр движка на вызов, отмена исключением из callback. `core/diarization.py` (pyannote) остаётся за GUI.
- - `stt_providers.py` / `gigaam_device.py` / `gigaam_ctc_wrapper.py` / `gigaam_e2e_ctc_wrapper.py` / `whisperx_wrapper.py` / `whisper_batch.py` / `stt_errors.py` — torch-free контракт провайдеров и проверка `--device`; политика CUDA для GigaAM (порог свободной VRAM для `auto`, распознавание CUDA OOM, освобождение кэша); lazy wrapper `ai-sage/GigaAM-Multilingual` revision `ctc` (только CPU) с общим device-механизмом (загрузка на CPU → перенос на CUDA, OOM → CPU с повтором окна, `empty_cache` при выгрузке); наследник для `ai-sage/GigaAM-v3` revision `e2e_ctc` (патчи transformers 5.x на загрузке, fp32, CUDA разрешена). ## Решения по STT-пулу (не поднимать повторно без новых данных)
- CPU-воркер — процесс с одной моделью и потоками-слотами; GPU-воркер — батчинг между заданиями; GigaAM на CUDA из нескольких потоков запрещён (порча качества по бенчмарку).
- В пуле устройство строгое: `cpu` никогда не на GPU, `cuda` на CPU только при подтверждённом отсутствии CUDA (с предупреждением), `auto` уходит на CPU по ETA (порог 0.8). Клиентского CPU-recovery нет.
- Имена моделей Whisper не меняют регистр (`auto` → `large-v3`); приоритет: класс со старением каждые `priority_aging_s`, внутри класса чередование вызовов; начатые задания не вытесняются.
- Тесты пула используют только фейковые движки и временные корни очередей; реальные модели — только в `heavy_ml` тестах по одной за раз.
- Managed-запуск (решение Архитектора 2026-10-29): только `ASKVLM_EXTERNAL_SUPERVISOR_MANAGED=1`, заданный клиентам и супервизору, передаёт жизненный цикл внешнему менеджеру служб (`askvlm-external-transcriber.service`). Клиент не создаёт/не перезапускает супервизор и ждёт первый heartbeat в прежнем ограниченном startup budget (также при бесконечном timeout вызова); при недоступности возвращает обычный unavailable/11 с диагностикой сервиса и очереди. Managed-супервизор не выходит по idle linger, TTL моделей сохраняется. `INVOCATION_ID` бота не включает этот режим. Общий корень кэшей моделей задаёт `ASKVLM_CACHE_DIR` (на сервере — абсолютный путь на SSD); без переменной остаётся `<project>/.cache`, очередь отдельно задаёт `ASKVLM_EXTERNAL_QUEUE_DIR`. Без managed-флага запуск прежний.
- Диаризация в CLI (sherpa-onnx, CPU): `process()` sherpa-onnx 1.13.8 держит GIL весь прогон и игнорирует возвращаемое значение callback, поэтому воркер диаризации — один слот на процесс (масштабирование процессами), а отмена — исключением из callback (стадия сегментации не прерывается; при обновлении sherpa перепроверить). Потоки задаёт `diarization.threads_per_slot` в конфиге пула (по умолчанию 4, без `--threads`). Метки `speaker_00…` перенумерованы по первому появлению (сырые индексы sherpa не непрерывны). Префиксы `speaker_xx: ` в тексте — только при 2+ голосах, назначенных сегментам; сегмент без пересечения — `"speaker": null`. Whisper-опции с GigaAM — ошибка (код 2). JSON в stdout — ASCII (`\uXXXX`), файлы — UTF-8. В `--no-daemon` диаризация идёт до загрузки STT-модели (одна модель за раз).
- Тесты с SAPI-голосами: «Microsoft Pavel» виден только PowerShell 7 (`pwsh`), а Windows PowerShell 5.1 — нет; эталонная пара для диаризации — Pavel + «Microsoft Zira Desktop» (по заметке навыка hardsub голоса одного движка, Pavel + Irina из OneCore, диаризатор не разделяет; Pavel + «Microsoft Irina Desktop» разделяются и дают русский диалог из двух голосов).
- Лимит Job Object воркера действует и на его детей (ffmpeg): он равен резерву commit плюс `memory.child_headroom_gib` (запас не резервируется планировщиком). Воркер до создания движка отключает окна ошибок Windows (`winjob.suppress_error_dialogs`, `SetErrorMode`), дети наследуют режим: не запускай детей воркера с `CREATE_DEFAULT_ERROR_MODE`, иначе отказ загрузки ребёнка под лимитом (`0xC000012D`) снова повесит модальное окно и задание до `cancel_grace_s`. Отчёт Job Object о лимите (от любого процесса job) — событие ресурса: оценка commit растёт один раз на воркер; готовый воркер уходит в `retiring`, если его лимит не поднят на ходу (живое повышение — только при первом отчёте о дочернем процессе, см. ниже), загружающийся — нет, чтобы ключ на потолке оценки не перезапускался по кругу; задания, шедшие под отчитавшимся лимитом, с `transcribe_failed` повторяются как `memory_limit`, остальные виды ошибок не переклассифицируются.
- Память долгоживущего GPU-воркера на torch (GigaAM на CUDA) ограничена: кэши планов по формам входа имеют границы `gpu.cufft_plan_cache_max_size` (32, ставится после загрузки модели) и `gpu.cudnn_v8_lru_cache_limit` (256, только через переменную окружения запуска `TORCH_CUDNN_V8_API_LRU_CACHE_LIMIT`: torch читает её один раз, при первой свёртке), а кэш аллокатора CUDA освобождается потоком батч-цикла после `gpu.idle_cache_release_s` простоя. Каждый результат воркера несёт снимок памяти (`memory`, телеметрия: битый снимок не делает результат невалидным, версия протокола не меняется), супервизор пишет его в строку `result published` вместе с пиком Job Object. `core/pipelines.py` импортирует `core.whisperx_wrapper` (faster-whisper/CTranslate2 со своим cuDNN) только при сборке Whisper-конвейера: не возвращай импорт на уровень модуля, иначе GigaAM-воркер снова загрузит CTranslate2.
- Границы памяти одного воркера: commit — жёсткий лимит Job Object (резерв + `child_headroom_gib`), мягкая замена при private bytes воркера ≥ `memory.recycle_commit_fraction` × резерв (по умолчанию 1.0: доля ниже 1 может вызывать замену после каждого задания, когда резерв выучен по пикам) и не больше одного живого повышения лимита на воркер (`memory.live_cap_raise`); VRAM GPU-воркера на torch — жёсткий потолок аллокатора (`gpu.vram_cap`, резерв VRAM + `gpu.vram_cap_margin_gib`, ставится до загрузки модели, переполнение идёт путём `cuda_oom`) и возврат кэша в простое; кэши планов ограничены; любой остаточный рост (CUDA-контекст, аллокатор CTranslate2, утечки ниже порога) — потолок времени жизни `lifecycle.worker_max_uptime_h` (12 ч, отсчёт от запуска, `retiring` без прерывания заданий, одна замена на воркер). `CT2_CUDA_ALLOCATOR`/`CT2_CUDA_CACHING_ALLOCATOR_CONFIG` не задаём: документация CTranslate2 не описывает ни потолка на процесс, ни возврата памяти у `cuda_malloc_async` (по умолчанию при CUDA ≥ 11.2), а `cub_caching` ограничивает лишь кэш свободных блоков (200 МБ), не живые выделения. Живое повышение: только у готового воркера при первом отчёте Job Object и только если отчёт назвал дочерний процесс, а не сам воркер — Windows шлёт `JOB_OBJECT_MSG_JOB_MEMORY_LIMIT` лишь о первом отказе каждого процесса (замер на Windows 11 22631: ни поднятый лимит, ни снятие и возврат флага, ни повторная привязка порта новое уведомление тому же процессу не дают), поэтому после отказа самого воркера его второе попадание в лимит не было бы видно. Резерв = `reservation_for` после `_bump_memory_once` (не выше потолка оценки), рост проходит `scheduler.commit_growth_blockers` (бюджет, guard, критический порог); `WorkerJob.set_memory_limit` делает query-modify-set (флаги, включая kill-on-close, сохраняются) и взводит одноразовый отчёт пакетом `_REARM_KEY` до установки нового лимита (порт FIFO: уведомления о старом лимите отбрасываются). Отказ повышения и второй отчёт — прежний путь `retiring`; отказ попытки, шедшей в момент повышения, повторяется как `memory_limit`, но воркер не отставляется. Отдельного порога замены по VRAM нет: снимок результата берётся до возврата кэша в простое и меряет кэш, а не утечку, а жёсткий потолок уже ограничивает рост. Жёсткого потолка VRAM у Whisper на GPU (CTranslate2) нет: его ограничивают физическая память GPU и потолок времени жизни. После живого повышения выход воркера считается упором в лимит только при отчёте о поднятом лимите или пике у поднятого лимита: прежний отчёт уже отработан повышением.
- Число воркеров pytest-xdist по умолчанию 3 (`-n 3` в `pyproject.toml`, переопределение — `-TestWorkers N`). Прежний `-n auto` давал ~16 воркеров и 40–51 ГБ commit и однажды исчерпал лимит commit системы; измеренный пик дерева pytest на `-Fast` с 3 воркерами — ~6.4 ГБ commit. Полный (не-`-Fast`) прогон дополнительно гоняет `heavy_ml` с реальными моделями: перед ним проверяй свободный commit.

## Контроль качества
- Основная команда проверки `. .venv/Scripts/Activate.ps1 && ./run.ps1 -SkipLaunch -Fast` обеспечивает быстрый чекап.
- - Используй `./run.ps1 -SkipLaunch` для запуска всех проверок.
- - Ты обязан запустить хотя бы одну из этих команд в конце своей работы для верификации качества кода.
- - Запускай проверки иными способами только если ранера недостаточно.
- - `-TestWorkers N` — число воркеров pytest-xdist (по умолчанию 3; `N` — целое ≥ 0 или `auto`; `0` — прогон в одном процессе без воркеров, например под отладчиком). `auto` на этой машине даёт ~16 воркеров и 40–51 ГБ commit: не использовать без нужды.
- - `-Cli` — исключает тесты, которым нужен Qt GUI (`pytest -m "not gui"`); сочетается с `-Fast` в одно `-m`-выражение. Тесты, которым нужен Qt (`QApplication`, `MainWindow`, `qtbot`, код из `gui/`), обязаны иметь маркер `gui`; линтеры флаг не затрагивает. Флаг не гарантирует, что Qt вообще не импортируется: часть немаркированных тестов импортирует `PySide6` или создаёт `QApplication`, не используя его.
- - Тесты идут headless: `tests/conftest.py` ставит `QT_QPA_PLATFORM=offscreen` до создания `QApplication`, окна не показываются. Для отладки с видимыми окнами задай `ASKVLM_TESTS_SHOW_GUI=1` (заранее заданный `QT_QPA_PLATFORM` тоже сохраняется).
- Запускай терминал с `block_until_ms=600000` или больше.
- Если терминал не уложился в таймаут, итеративно решай убивать или ждать: для ожидания запускай паузу на 5 минут.
