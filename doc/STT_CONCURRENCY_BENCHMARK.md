# Бенчмарк параллельности STT (2026-10-14)

## Зачем

Перед переходом `external-transcribe` с демона-одиночки на супервизор с пулом воркеров нужно было выбрать устройство воркера:

- **P** — N отдельных процессов, у каждого своя копия модели;
- **S** — один процесс, одна модель, N потоков над общими весами;
- **B** — батчинг: несколько входов за один прогон модели.

Замер проводился на целевом ПК, загрузка повышалась до тех пор, пока не падала скорость или качество.

## Инструмент

`tools/benchmark_stt_concurrency.py` (пакет `tools/stt_concurrency/`):

- `run` — фиксированная матрица конфигураций;
- `sweep` — поиск точки насыщения по группам (движок × устройство × режим × потоков на поток);
- `combo` — две конфигурации одновременно (CPU + GPU), замедление каждой стороны против одиночного замера;
- `memory-growth` — рост памяти одного долгоживущего GPU-воркера пула по заданиям (раздел «Рост памяти долгоживущего GPU-воркера»);
- `summarize`, `list`, `--dry-run` (ничего не пишет).

Безопасность:

- перед шагом — проверка свободного commit и VRAM;
- на время шага — Job Object с жёстким лимитом commit на всё дерево процессов (исход `memory_cap` = точка насыщения);
- сторож свободного commit системы (`system_commit_low`);
- дети умирают вместе с родителем;
- продолжение прогона с отпечатком входных данных (результаты с другим отпечатком перемеряются).

Пример (пути к данным передаются аргументами):

```powershell
python tools/benchmark_stt_concurrency.py sweep --clips-dir <папка WAV 16 kHz> --manifest <JSONL с эталонами> --out-dir <вне репозитория> --dry-run
python tools/benchmark_stt_concurrency.py sweep --clips-dir <...> --manifest <...> --out-dir <...>
python tools/benchmark_stt_concurrency.py combo --auto-combos --clips-dir <...> --manifest <...> --out-dir <...>
```

## Условия замера

- Ryzen 9 5950X (16 ядер / 32 потока), 64 ГБ RAM, RTX 3070 8 ГБ, Windows 11, Python 3.11.9, torch 2.10 + cu128, faster-whisper 1.2.1.
- Рабочий бот и его зависимости остановлены, фон минимальный.
- Данные: FLEURS ru_ru test, первые 120 клипов (в среднем ~11 с), WER против `ref_fleurs_norm`.
- Шаг длится не меньше 45 с и не меньше 12 клипов на поток.
- Декодирование Whisper одинаковое для всех режимов: beam 5, без VAD, без кондиционирования, temperature 0.
- Один прогон без повторов; xRT = секунды аудио / секунды стены.

## Результаты: максимумы по группам

«Максимум» — лучший шаг группы. Часть CPU-групп упёрлась не в насыщение, а в предел машины (N×T ≤ 32 логических потоков, на последнем шаге прирост ещё 8–10%). Скан GigaAM P×1 остановила проверка памяти на P12×1 (+26% на последнем шаге), поэтому P16×1 не замерен.

| Движок, устройство | Выбранный режим | xRT | Память (commit / VRAM) | Альтернативы |
|---|---|---|---|---|
| GigaAM-v3 e2e_ctc, CPU | **S8×4** (1 процесс, 8 потоков по 4) | 68.7 | 4.1 ГБ | P8×4: 68.6× при ~30 ГБ; P12×1: 65.1× при 42 ГБ; экономно S12×1: 64.1× при 3.7 ГБ |
| GigaAM-Multilingual ctc, CPU | **S8×4** | 69.1 | ~3.5 ГБ | P8×4: 67.6× |
| Whisper small int8, CPU | **S6×2** | 11.0 | 2.6 ГБ | P6×2: 11.2× при 8.9 ГБ; батч B2×16: 7.1× |
| GigaAM-v3 e2e_ctc, CUDA | **компромисс**: B8 (батч из 8 окон в 1 процессе) — меньше памяти; P3 (3 процесса) — быстрее | B8: 137.5; P3: 179.3 | B8: 6.1 ГБ / +1.7 ГБ; P3: 17.4 ГБ / +4.7 ГБ | B16: 138×; P2: 130× при 12 ГБ / +3.1 ГБ |
| Whisper small fp16, CUDA | **B4** (батч из 4 клипов) | 35.4 | 3.1 ГБ / +1.3 ГБ | P2–P3: ~25× (GPU загружен на 95%); B8 отклонён по качеству |

При общем бюджете 16 потоков (N×T = 16, ближе к реальной работе рядом с другими воркерами):

| Движок, CPU | S4×4 | P4×4 |
|---|---|---|
| GigaAM-v3 e2e_ctc | 57.9× при 4.1 ГБ | 58.8× при 15.4 ГБ |
| GigaAM-Multilingual ctc | 59.5× | 58.4× |
| Whisper small int8 | 10.7× при ~2.2 ГБ | 11.1× при ~6.1 ГБ |

Наблюдения:

- **CPU.** При одинаковом N×T потоки над общими весами дают ту же скорость и те же тексты, что и процессы, при памяти в 3–12 раз меньше. GigaAM выдаёт одинаковые тексты во всех конфигурациях. Whisper int8 зависит от числа потоков на поток: совпадение с P1×16 64–88%, WER колеблется до 1.5 п.п.
- **GigaAM на CUDA, режим S (потоки) испорчен.** При S2 WER по всему корпусу шага 13.15% против 4.24% на первом шаге; на общих клипах рост 0.53 п.п.; совпадение текстов 88.5%, средняя похожесть 0.902. Этот режим не используется.
- **GigaAM на CUDA, по-видимому, ограничен не GPU** (загрузка 16–38%), а CPU-частью каждого процесса (~2.7 ядра на процесс). Рост скорости дают и батчинг, и дополнительные процессы.
- **Whisper на CUDA при батче 8** даёт WER +0.61 п.п., поэтому предел — 4. Батчинг применяется только к клипам ≤30 с. На длинных файлах фиксированные куски по 30 с теряли часть текста: похожесть с последовательным эталоном 0.945 в раннем пробном прогоне.

## Результаты: CPU и GPU одновременно

| Пара | GPU-сторона: xRT (соло) | CPU-сторона: xRT (соло) | Сумма | Загрузка CPU |
|---|---|---|---|---|
| GigaAM CUDA P3 + GigaAM CPU S8×4 | 79 (179), −56% | 58 (68.7), −16% | 137 | 100% |
| GigaAM CUDA P3 + Whisper CPU P6×2 | 127 (179), −29% | 8.5 (11.2), −24% | 136 | 53% |
| Whisper CUDA B4 + GigaAM CPU S8×4 | 17.8 (35.4), −50% | 65 (68.7), −5% | 83 | 98% |
| Whisper CUDA B4 + Whisper CPU P6×2 | 22 (35.4), −37% | 10.5 (11.2), −7% | 33 | 44% |

Одновременная CPU-нагрузка заметно тормозит GPU-воркеры, даже при неполной загрузке CPU. Причина не выделена: это может быть конкуренция за ядра, пропускная способность памяти, PCIe или накладные расходы драйвера. Для GigaAM сумма пары (137×) меньше, чем один GPU (179×).

## Решения для пула воркеров

1. **CPU-воркер:** один процесс на конфигурацию, слоты = потоки над общими весами. У Whisper это `num_workers`, у GigaAM — потокобезопасный путь инференса.
2. **GPU-воркер (рабочая гипотеза).** Процесс с батчингом: у GigaAM до 8 окон, у Whisper до 4 клипов ≤ 30 с; длинные файлы Whisper идут последовательно. Можно держать несколько таких процессов в пределах лимита GPU-слотов. Для GigaAM это компромисс: один батчующий процесс (137×) экономнее трёх простых процессов (179×), а режим «несколько процессов, в каждом батч» ещё не замерялся. Его нужно замерить при реализации пула. Потоки на CUDA для GigaAM запрещены.
3. **Общий бюджет CPU-ядер** учитывает CPU-часть GPU-воркеров: у GigaAM ~2.7 ядра на процесс, у Whisper ~1–2. Перелив на CPU не должен отнимать эти ядра. Ориентир для CPU-конфигураций при общем бюджете — строки «16 потоков» выше.
4. **Начальные коэффициенты планировщика** — из таблиц выше. Коэффициенты замедления берутся из совместных прогонов.

## Рост памяти долгоживущего GPU-воркера (2026-10-16)

### Зачем

Долгоживущий GPU-воркер `gigaam-e2e-ctc/ai-sage/GigaAM-v3@e2e_ctc/fp32/gpu` в продакшене рос примерно на 1 МБ commit за задание (~120 МБ/ч, корреляция с аптаймом 0.96) и доходил до лимита Job Object. Нужно было найти механизм роста, проверить, останавливают ли его границы памяти пула (`gpu.cufft_plan_cache_max_size`, `gpu.cudnn_v8_lru_cache_limit`, `gpu.idle_cache_release_s`, `gpu.vram_cap`), и сравнить torch 2.10.0 с 2.14.1.

### Инструмент `memory-growth`

Команда запускает один настоящий воркер пула штатным путём: `default_worker_launch` и `WorkerProcess` (свой Job Object с лимитом commit = резерв + `memory.child_headroom_gib`), фабрика движков `GigaamGpuBatchEngine`, `spec` из проверенного конфига пула, seed-оценок и лимитов, как его строит супервизор. Потом подаёт N заданий строго по одному: следующее уходит после результата предыдущего, при желании после паузы. Супервизор не участвует, потому что его замена воркера (порог `memory.recycle_commit_fraction`, живое повышение лимита, потолок аптайма) скрыла бы рост. Вместо этого сводка показывает, на каком задании сработал бы порог замены.

Входы синтетические. Источник — русская речь SAPI-голоса «Microsoft Pavel» через `pwsh` или файл `--source`, например `tests/fixtures/test_video_short.mp4`. Источник повторяется в один длинный WAV, и FFmpeg нарезает из него задания по seed-смещениям, в Ogg Opus 16 кГц моно, как голосовые Telegram. `--durations varied` берёт длительность равномерно из `[--duration-min-s, --duration-max-s]` (по умолчанию 1–60 с, с точностью до миллисекунды, поэтому у каждого задания своя форма входа). `--durations fixed` даёт всем заданиям одну длительность. Записи пользователей не используются.

На каждое задание пишутся снимок памяти из результата (private bytes, CUDA reserved/allocated/max reserved, число планов cuFFT), пик Job Object, private bytes перед заданием, занятая VRAM всего GPU по nvidia-smi (`--no-gpu-sample` выключает) и время. Сводка содержит:

- базу после загрузки;
- наклон МНК на задание и в час по последним 80% заданий;
- сдвиг медианы последних 20% заданий против предыдущих 20% («плато» — сдвиг не больше допуска, по умолчанию 16 МиБ);
- максимумы, траектории cuFFT и CUDA, пропускную способность, порог замены пула.

Защита: прогон стартует, только если свободно не меньше 20 ГиБ commit и 3 ГиБ VRAM (`--min-free-commit-gib`, `--min-free-vram-gib`) и лимит Job Object воркера помещается в свободный commit за вычетом `--commit-reserve-gib` (по умолчанию 12). Эта проверка идёт до всего остального, в том числе до пробы версий torch. Правила по commit повторяются после нарезки входов, непосредственно перед запуском воркера: нарезка может длиться минуты, пока другие процессы занимают память. Отказ на любом из этих шагов завершает прогон с кодом 3 до запуска воркера и записывается в `run.json` (`guard` или `spawn_guard`). Идущий замер останавливается, когда свободный commit падает ниже `--commit-reserve-gib`.

Коды выхода:

- 0 — все задания выполнены, сводка записана;
- 1 — прогон остановлен раньше;
- 2 — неверный ввод или не удалось подготовить входы (статус `inputs_failed`; в папке прогона остаются `run.json` и сводка);
- 3 — отказ проверки ресурсов;
- 4 — все задания выполнены, но сводку записать не удалось;
- 130 — Ctrl+C.

Остановленный раньше прогон завершается с кодом 1, даже если его сводку записать тоже не удалось. Конфиг пула берётся из кода (`stt_pool.json` и `ASKVLM_STT_POOL_CONFIG` не читаются) или из `--pool-config`. Отдельные ключи переопределяет `--pool-set PATH=VALUE`. `--gpu-memory-bounds library` выключает все четыре GPU-границы, то есть даёт поведение до их появления. Результаты пишутся в `.cache/stt_memory_growth/<время>-<метка>/` (`run.json`, `results.jsonl`, `results.csv`, `summary.json`, `summary.md`, `worker.log`). `summarize --out-dir <папка прогона>` пересчитывает сводку.

```powershell
python tools/benchmark_stt_concurrency.py memory-growth --jobs 2000 --label A --idle-gap-s 16 --idle-gap-every 50
python tools/benchmark_stt_concurrency.py memory-growth --jobs 2000 --label B --gpu-memory-bounds library
python tools/benchmark_stt_concurrency.py memory-growth --jobs 2000 --label C --gpu-memory-bounds library --durations fixed --fixed-duration-s 13
python tools/benchmark_stt_concurrency.py memory-growth --jobs 1000 --label V2 --gpu-memory-bounds library --pool-set gpu.cudnn_v8_lru_cache_limit=256
```

### Условия

- Та же машина, драйвер 610.88 (CUDA 13.3). Стек 2.10 — рабочий `.venv`: torch 2.10.0+cu128 (CUDA 12.8, cuDNN 9.10.2), transformers 5.14.1, numpy 1.26.4. Стек 2.14 — временный venv: torch 2.14.1+cu130 (CUDA 13.0, cuDNN 9.24.0), torchaudio 2.11.0 (последний выпуск torchaudio, новее нет), остальные пакеты тех же версий. Конфиг пула — значения по умолчанию из кода: 8 дорожек, резерв из seed-оценки (commit 7.0 ГиБ, лимит Job Object 8.0 ГиБ, порог замены 7.0 ГиБ, VRAM 2.2 ГиБ, потолок аллокатора 3.2 ГиБ).
- Одновременно работали прод-бот (его GPU-воркер на старом коде, private bytes ~7.0 ГиБ) и тесты другой команды. Поэтому скорость сравнима только в паре прогонов подряд (T1–T3). Защита commit остановила A на 1377-м задании и два первых запуска (B на 65-м, A′ на 40-м). Последующие прогоны шли с `--commit-reserve-gib 8`.
- N = 1000–2000 вместо 300: задание идёт ~0.3 с, а длинный прогон точнее показывает наклон.
- В A и A′ после каждого 50-го задания стоит пауза 16 с, это дольше `gpu.idle_cache_release_s` = 15 с. При подаче подряд возврат кэша не срабатывал бы никогда, а в проде паузы между голосовыми обычны.
- Длительности `varied` (seed 1) одинаковы во всех прогонах; ~32% заданий короче окна 20 с. Только они дают новую форму входа: окна длинных заданий дополняются нулями до 20 с.

### Выводы

1. **Механизм (уверенно).** Рост — это host-память процесса (private bytes), а не кэш CUDA. Его вызывает разнообразие форм входа. При одной длительности (C) за 2000 заданий не прибавилось ни байта, то есть утечки на задание нет. При разных длительностях без границ (B) рост +0.79 МиБ/задание без плато, а reserved/allocated постоянны. Почти весь рост даёт кэш планов cuDNN v8 (`TORCH_CUDNN_V8_API_LRU_CACHE_LIMIT`, по умолчанию 10000). Граница только cuFFT (V1) рост не меняет: на заданиях 201–1000 у V1 +1.15 МиБ/задание, у B +1.17. Граница только cuDNN (V2) рост останавливает: +0.02 МиБ/задание, хотя планов cuFFT 291 и их число растёт. Планы cuFFT стоят ~0.1 МиБ каждый, это заметно только при тысячах форм. Число планов cuDNN снаружи не видно. Если по оценке torch на план приходится ~200 КиБ, лимит 10000 даёт ~2 ГиБ, то есть столько, сколько B набрал к 2000-му заданию. Насыщался ли B, не проверено. При любом ответе граница по умолчанию выше бюджета воркера: порог замены 7 ГиБ, лимит 8 ГиБ.
2. **Границы пула рост останавливают (уверенно).** A: +0.006 МиБ/задание, плато 5471 МиБ (5.34 ГиБ) с ~140-го задания до 1377-го. CUDA reserved ~1.4 ГиБ при потолке 3.2 ГиБ. A′ (2.14) тоже ровный. Запас до порога замены (~1.7 ГиБ над уровнем) и до потолка VRAM (~1.8 ГиБ) покрывает кратковременный скачок после возврата кэша. Остаточного неограниченного роста на этих входах нет. Потолок аптайма 12 ч остаётся страховкой от того, что замер не покрывает: другие длительности и языки, многочасовые файлы, рост контекста CUDA за сутки.
3. **torch 2.14.1 (средняя уверенность).** Памяти меньше: −0.3 ГиБ commit после загрузки, −0.3…−0.5 ГиБ на уровне, −0.38…−0.45 ГиБ CUDA reserved, −0.4…−0.5 ГиБ VRAM всего GPU. Рост без границ примерно в 20 раз меньше (на заданиях 201–1000 +0.056 МиБ/задание против +1.17), но границы пула нужны и там: число планов cuFFT растёт так же. Скорость не выше: в паре подряд 2.14 медленнее на 8–15%, но это один прогон, а разброс 2.10 между T1 и T3 составил 8%. Прогоны varied под чужой нагрузкой выглядели в пользу 2.14, но они шли в разное время и потому несравнимы. Совместимость: GigaAM с патчами transformers 5.14.1 работает. torchaudio застыл на 2.11.0. Remote code модели требует импортируемого `pyannote` (`check_imports` transformers), как и в рабочем venv. Переход потребует сменить закрепление `torch>=2.10,<2.11` в `pyproject.toml` и CUDA-ремонт torch 2.10 + cu128 в `run.ps1`/`build.ps1`.

### Ограничения замера

- Один прогон на конфигурацию. Сравнение скорости 2.10 и 2.14 — одна тройка T1–T3.
- Распределение длительностей равномерное 1–60 с, а не продовое. Язык и голос один.
- Пик Job Object за время жизни процесса — накопленный максимум, а не пик одного задания.
- VRAM всего GPU включает чужие процессы. Точнее память воркера описывает CUDA reserved.
- Сырые данные лежат вне Git, в `.cache/stt_memory_growth/` рабочей копии, где шёл замер. Прогоны `20261016T…-<метка>`: A, B, C, V1, V2, A′ = `A-varied-pool-t214`, B′ = `B-varied-library-t214`, T1–T3. У запуска `20261016T184215Z-A-varied-pool-t214` загрузка упала, потому что во временном venv не хватало `pyannote`. Его `summary.json` пересобран со статусом `unknown`.
